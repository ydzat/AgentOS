# Agent OS 架构思辨：从政治体制类比到路径选择

> 日期: 2026-05-27
> 来源: 与 Claude (Opus 4.6) 的深度讨论

## 1. 出发点：政治体制与软件架构的类比

### 竖切 vs 横切

在政治学中：

- **横切政体 (Horizontal Separation)** — 按权力类型切分：立法、行政、司法三权分立。同一层级内，不同机构管不同性质的权力。
- **竖切政体 (Vertical Separation)** — 按领域/地域切分：联邦制下，每个州/省拥有自己的立法、行政、司法，是一个功能完整的自治单元。

### Linux Kernel 是"竖切"的

Linux Kernel 的子系统划分（MM、VFS、Scheduler、Block Layer）是竖切思路的典型体现：每个子系统内部自成体系，有自己的数据结构、逻辑、接口规范，通过明确定义的边界接口通信。核心思想是 **Separation of Concerns (SoC)**。

### 政治系统为什么是"横切"为主

| | 软件工程 | 政治系统 |
|---|---------|---------|
| 对象 | 被设计的抽象系统 | 自然演化的社会系统 |
| 领域边界 | 可以人为划定，清晰 | 天然纠缠，模糊 |
| 核心风险 | 复杂度失控 | 权力集中 |
| 解法 | 竖切——领域自治 | 横切——权力制衡 |

人类社会的各个领域（经济、教育、医疗）天然纠缠在一起，无法像代码一样画接口。所以政治系统最危险的不是"复杂度高"，而是某个节点集中了过多权力。横切正是为此而生。

### 有趣的反证

当软件系统开始模拟社会复杂性时（如大型电商系统），竖切也会遇到问题，催生了 Cross-cutting Concerns 和 AOP（面向切面编程）——向政治系统的架构逻辑靠拢。

## 2. "单位"制度的启示

### 单位的本质

中国的"单位"制度将原本依赖于"人"的工作转变为依赖于"工作"的工作：

- **传统社会（人治）：** 权力依附于人——换一个人，整个系统可能就塌了
- **单位制度（制度治）：** 权力嵌入岗位和职能——人员可以替换，单位持续存在，使命不变

用组织学的语言说：**"单位"是一个以使命 (mission) 而非以功能 (function) 为边界的自治组织单元。**

### 从"按功能切"到"按使命切"

传统 SoC 是"按功能切"——每个模块定义的是"我管什么类型的操作"。

"单位"是"按使命切"——每个单元定义的是"我完成什么任务"。它内化了所有需要的功能（人事、财务、后勤），因为边界由使命决定。

这个思路在软件中已有体现：

- **Domain-Driven Design** 的 Bounded Context 本质上就是在定义"单位"
- **Microservices** 以业务使命为边界的自治服务

## 3. SoC 是否过时？

**SoC 作为原则，不会过时。** "关注点分离"说的是"不同的关注点应该被隔离"——单位制恰恰也是一种关注点分离，只是分离的粒度从"功能"提升到了"使命"。

**SoC 作为"按技术功能竖切"的实践，确实在过时。** 把"所有数据库操作"放在一个模块里、把"所有网络请求"放在一个模块里——这种传统切法在复杂系统中已证明有问题。

> 这不是 SoC 的过时，而是 SoC 的**升维**——分离的关注点从"技术功能"提升到了"组织使命"。

## 4. Agent OS 与传统系统的本质区别

### 已经存在的东西

讨论中审阅了这个思想——它是否实际上已经被包括在传统软件工程中？答案是：**很大程度上，是的。**

| Agent OS 的概念 | 已有的前辈 |
|----------------|-----------|
| 每个 Agent 是自治单元 | Actor Model (Carl Hewitt, 1973) |
| Agent 有子 Agent | Supervision Tree (Erlang/OTP, 1986) |
| 资源配额和预算管理 | Capability-based Security (1960s, Hydra OS) |
| Agent 间结构化通信 | CSP (Hoare, 1978) → Erlang message passing |
| 使命定义 + 生命周期管理 | Kubernetes (Pod spec, health check, restart) |
| 按使命/领域划边界 | DDD Bounded Context (Eric Evans, 2003) |
| 服务注册、发现、治理 | Service Mesh (Istio, Linkerd) |

### 什么是真正新的

剥掉所有已有概念，Agent OS 真正不可还原的新东西只有一个：

> **被管理的实体，其使命是开放式的 (open-ended mission)。**

| 实体类型 | 使命性质 |
|---------|---------|
| 进程 | 执行这段代码，返回结果（确定性） |
| 微服务 | 处理某类请求，维护某类数据（确定性） |
| Actor | 响应某类消息，维护某个状态（确定性） |
| **Agent** | **帮我搞定这件事（非确定性、开放式）** |

这带来了全新的治理挑战：

1. **使命怎么表达？** — 可能是自然语言，可能是目标函数
2. **信任边界怎么划？** — Agent 会"创造性地"寻找解决方案
3. **冲突怎么仲裁？** — 语义层面的目标冲突，不是死锁
4. **使命偏移怎么检测？** — Agent 可能偏离原始意图
5. **自由度怎么动态调整？** — 传统 OS 没有这个概念
6. **组织记忆怎么积累？** — 从历史使命中学习

### 与 Claude Code 等工具的区别

单用户、单使命场景下，Agent OS 和 Claude Code 没有本质区别。真正的差异在于：

- **持久运行** — Agent 是"一个岗位"，不是一次对话
- **大量并发** — 几十个 Agent 同时竞争资源
- **信任隔离** — 不同 Agent 有不同的权限域
- **跨组织协作** — Agent 属于不同的 OS 实例，需要跨机器治理

## 5. 上下文引擎的定位

### 与 VMM 的类比

上下文引擎参考了 OS VMM 的设计思想：

| | VMM | 上下文引擎 |
|---|-----|-----------|
| 有限资源 | 物理内存 | 上下文窗口 |
| 无限存储 | 磁盘 | 归档记忆 |
| 调度目标 | 哪些页在内存里 | 哪些 message 在上下文里 |

### 应该留在应用层

上下文调度目前处于早期阶段（策略还在快速演化），不适合固化到系统层：

- 页的大小不固定（message 大小差异巨大）
- 调度依据是语义相关性（不是 LRU/LFU）
- 替换代价不可预测

建议的分层：

- **系统层（未来 Agent OS）：** 分配、隔离、配额、保护（类似 mmap）
- **应用层（上下文引擎）：** 所有"聪明"的调度策略

## 6. 具身智能：为什么需要系统层

### 机器人领域的现状（2025-2026）

- VLA（视觉-语言-动作）模型爆发，Agent 能把自然语言指令直接转化为物理动作
- 无需示范的 LLM 直接控制机器人的研究已发表 (2026.01)
- 学术界已提出 LLM 控制机器人的"语义拒绝服务攻击"问题
- 2025 年被视为人形机器人量产元年

### 物理世界的不可撤销性

```
软件 Agent 犯错 → 文件写错了、API 调多了 → 可以撤销
物理 Agent 犯错 → 机械臂撞到人 → 不可撤销
```

对于不可撤销的后果，应用层的权限检查不够——需要硬件+内核联手的强制隔离。

### 从 ROS 的历史看

- ROS 1 (2007): 纯应用层框架，没有实时保证，适合研究不适合生产
- ROS 2 (2017): 引入 DDS 实时通信，开始关注安全性，但仍跑在通用 OS 之上
- 工业机器人的真实选择: RTOS (QNX, VxWorks, Zephyr)

ROS 1 → ROS 2 的转变，恰好对应了"应用层不够，需要系统层"。

### Agent + 机器人比传统机器人更危险

Agent 可能"创造性地"找到危险的方式来完成任务——这在传统确定性控制的机器人中不存在。

## 7. 结论：路径 C

### 架构选择

```
路径 A（从内核开始做 OS）
  → 纯软件 Agent：太早，不需要
  → 具身 Agent：有意义，但单独走这条路太窄

路径 B（在 Linux 之上做治理框架）
  → 纯软件 Agent：完全够用
  → 具身 Agent：不够，缺乏实时保证和硬件隔离

路径 C（两者结合）← 选择
  → 纯软件部分跑在 Linux 上（应用层治理）
  → 具身部分跑在自研微内核上（系统层隔离）
  → 两层通过统一的 Agent Runtime 协议通信
```

### Agent OS 架构

```
Agent OS
│
├── 上层：治理框架（跑在 Linux 之上）
│   · 使命管理、Agent 派生、预算分配
│   · 上下文调度（智能的调度策略）
│   · 组织记忆、冲突仲裁
│   · 管理软件 Agent（纯数字世界的任务）
│
├── 中间：统一的 Agent Runtime 协议
│   · 不管 Agent 是软件的还是具身的，OS 看到的接口一致
│   · 类似 Linux 的 VFS——上层不关心底下是 ext4 还是 NFS
│
└── 底层：定制微内核（处理具身场景）
    · 实时调度（物理动作有 deadline）
    · 硬件级隔离（电机、传感器的 capability）
    · 确定性保证
    · 管理物理 Agent（机器人、IoT 设备）
```

### 类比定位

类似 Android 的设计：
- 上层应用框架跑在 Linux 之上
- 底层的 Linux 内核被深度定制过（Binder IPC, wakelock, 特殊调度器）
- 已经不是一个普通的 Linux 了

> **Agent OS = 一个定制微内核（处理物理 Agent 的实时性和隔离）+ 一个运行在 Linux 上的治理框架（处理软件 Agent 的使命管理），两者通过统一的 Agent Runtime 协议打通。**

### Rust 的适配性

- 微内核：Rust 的安全性和 `no_std` 能力
- 治理框架：同样用 Rust
- 两层可以共享类型定义和协议，但运行时完全独立
- Rust 的所有权和借用机制恰好能映射"单位对其资源的所有权"和"跨单位协作时的借用/授权"
